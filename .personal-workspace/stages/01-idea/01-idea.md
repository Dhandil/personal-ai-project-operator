# 个人 AI 项目工作台：方向草案

## Problem Statement

如何让一个人像运营小型项目组织一样，同时推进多个 Coding 或知识型项目：用户只负责提出想法、审批阶段目标和作出关键决策；不同 Agent 可以接任项目管理、设计、执行与审核等角色，在权限受控、状态连续、过程可追溯的条件下持续完成项目，而不依赖任何一次对话上下文？

## Recommended Direction

建设一个供个人使用的、任务驱动的 AI 项目工作台。

用户是最终决策者。项目负责人角色负责理解项目目标、提出阶段计划和短期目标；用户批准一个边界清晰的目标后，Agent 可以在该授权范围内连续拆解、执行、审核和交接，无需每完成一个小步骤就再次询问。

角色代表稳定的职责、权限和交付责任，不绑定具体 Agent。Agent 可以替换，但角色约束、任务状态、项目资料、决策记录和执行历史必须持续存在。

Task Card 是短期目标的授权与交接载体，但不是唯一的 Source of Truth。项目目标、架构、长期规范、关键决策及执行审计，应由各自适合的持久化信息载体负责。

## Key Assumptions to Validate

- [ ] Coding 与知识生产可以共享同一套核心治理流程  
  验证方式：分别选择一条真实工作流，比较它们能否共用目标审批、角色授权、任务状态、审核和交接机制。

- [ ] 用户批准一个短期目标后，Agent 能在该边界内持续推进，几乎不需要用户重复提示  
  验证方式：记录每个目标执行期间额外人工提示、纠偏和重新解释的次数。

- [ ] 角色职责可以转化为可执行的权限边界，而不只是提示词  
  验证方式：让审核角色尝试修改正式产物，确认修改无法进入 Source of Truth，并且尝试被完整记录。

- [ ] 隔离执行与受控合入带来的流程成本，低于错误修改、整体回滚和重新生产的成本  
  验证方式：比较现有直接执行流程与受控流程的操作步骤、返工次数和恢复成本。

- [ ] 项目负责人 Agent 能提出质量足够高的短期目标和任务计划  
  验证方式：检查用户对其提案的修改幅度，以及批准后因任务定义错误导致的返工。

## Provisional MVP Scope

第一版只验证一个核心闭环：

1. 用户提供项目想法或当前项目目标。
2. 项目负责人提出一个有明确边界的短期目标。
3. 用户审批、修改或拒绝该目标。
4. 获批目标被拆成连续任务，并分配责任角色。
5. Agent 通过统一受控入口，在隔离环境中执行。
6. 系统阻止未经授权的修改进入 Source of Truth。
7. 审核角色检查产物，生产角色处理审核问题。
8. 每次执行更新任务状态并生成交接信息。
9. 越权尝试、失败、恢复和正式变更均被记录。
10. 工作台在完成、Blocker 或需要关键决策时再通知用户。

MVP 应至少用一条知识生产流程和一条 Coding 流程验证共同模型，但不要求同时支持所有项目类型。

## Success Signal

用户批准短期目标后，新的 Agent 能够在没有历史聊天记录、也几乎不需要补充提示的情况下继续正确工作，直至：

- 目标完成；
- 遇到真实 Blocker；
- 或出现必须由用户决定的新问题。

同时满足：

- 未授权修改不能进入 Source of Truth；
- 所有越权尝试均有记录；
- 系统状态可以恢复；
- 因角色误解、版本混乱和交接缺失造成的返工显著减少。

## Not Doing（当前不做）

- 完整模拟公司的所有部门和职位——容易形成 Agent 官僚体系。
- 为每个角色固定一个长期 Agent——角色应稳定，Agent 应可替换。
- 让项目负责人自行决定产品方向和重大架构取舍——这些属于用户审批范围。
- 要求用户逐张批准所有细粒度任务——用户审批的是短期目标及授权边界。
- 一开始支持所有项目类型——先验证 Coding 与知识生产的共同治理模型。
- Calendar、Notes、Obsidian、GitHub 等全面集成——不是当前核心假设。
- 多用户协作与大规模 Agent 并发——个人单用户模式优先。
- 现在确定 UI、数据库或 Agent 技术框架——技术选型尚未开始。
- 把所有信息塞入 Task Card——会造成任务卡膨胀和上下文污染。

## Open Questions

- 什么程度的变化必须重新获得用户审批？
- 项目负责人如何判断“继续执行、遇到 Blocker、需要决策”？
- 短期目标应该多大，才能兼顾自主推进与风险控制？
- 哪些角色确实需要相互独立，哪些只是同一 Agent 的不同工作模式？
- 如何量化“几乎不需要再次提示”和“显著减少返工”？
