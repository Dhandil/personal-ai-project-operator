# 个人 AI 项目运营工具：需求探索总结

> 阶段：Phase 0 — 需求探索  
> 方法：`idea-refine` → `discovery-process`  
> 状态：已由用户确认  
> 日期：2026-08-13  
> 上一阶段产物：`方向草案.md`

## 1. 阶段结论

决定继续开发本项目（GO）。

本决定并不表示市场需求或最终方案已经得到验证，而是基于以下事实：

- 项目解决的是用户本人已经遇到的真实问题；
- 用户确定会把它作为个人练手和实际使用项目继续开发；
- 知识库项目与 Fashion Agent 项目都提供了真实案例；
- 项目可以在开发过程中通过 Dogfooding 持续校正，而不需要以更多前置实验作为开工门槛。

## 2. 产品范围修正

长期愿景可以是一个支持项目、学习、知识、笔记、文档和外部工具等能力的“个人 AI 工作站”。

当前项目不直接建设完整工作站，而是先独立建设其中一个明确能力：

> 个人 AI 项目运营工具。

它解决“个人如何通过可替换的 AI Agent 持续推进项目”，而不负责所有个人任务。

如果该工具经过实际使用证明有价值，未来再决定是否把它纳入更大的个人 AI 工作站。

## 3. 已确认的 Problem Statement

当我使用不同对话、角色和 AI Agent 持续推进个人项目时，项目的实时状态、当前任务、角色职责、执行进度和下一步往往依赖某个对话或我的记忆。

拆分多个 Agent 时，我必须手动整理上下文、启动角色并传递结果；集中在一个长对话时，职责又容易混合，新 Agent 难以接手。

我需要一种以项目而非对话为中心的运行方式，使项目状态和成果持续存在，让不同 Agent 可以正确接手、执行和交接，同时让我保留重要决策权并持续了解项目进度。

## 4. 目标用户与使用背景

当前目标用户只有项目创建者本人。

项目用于推进 Coding、知识生产以及未来其他类型的个人项目，同时锻炼产品、项目和架构决策能力。它不是商业项目，不追求企业级流程严谨性、多用户协作或组织级治理。

用户会使用 ChatGPT、Codex、Claude Code 等不同对话和 Agent。角色应表示稳定职责，而不应绑定某个具体 Agent 产品。

## 5. 真实案例与证据

### 5.1 Fashion Agent 知识库

现有流程已经具备任务清单、项目规范、生产者和独立审核者等基础结构，项目状态也会保存到仓库文件中。

仍然存在的问题：

- 每次打开 CLI，用户需要指定生产模式或审核模式；
- 新 Agent 需要知道先读取哪些入口和规范；
- 生产、审核、修改和复审之间的角色启动仍依赖用户；
- 规范文档较多，但没有根据角色、阶段和任务区分必读与按需读取；
- 动态进度在多份文件中重复记录，已经出现过期和冲突；
- 目录、命名和文件位置虽然已有规范，Agent 仍可能遗漏，说明仅写明规则不等于可靠执行；
- 曾发生审核者修改正式知识的事故，但当时用户指令可能存在歧义，因此暂时不能确认主要原因是权限失效还是角色切换不清。

该案例证明：文件作为 Source of Truth 基本可行，但 Bootstrap、上下文路由、角色推进、规则校验和权限边界仍不可靠。

### 5.2 Fashion Agent 应用项目

项目目标和架构已有明确文件，但已完成内容、当前进度和下一步没有持续更新。

为避免交接成本，开发过程主要集中在一个 Codex 对话中，导致：

- 前期规划与实际开发分散在不同对话；
- 产品、架构、前端、后端、开发和审核职责混合；
- 用户需要定期询问当前进度和后续规划；
- 如果换成新 Agent，只能重新扫描项目并自行推断现状。

该案例证明：维持一个长对话可以暂时回避交接，却会让项目状态和职责继续依赖对话。

## 6. 核心洞察

用户当前不仅是项目决策者，还被迫充当不同对话、角色和 Agent 之间的人工协调中枢，负责：

1. Bootstrap：告诉新 Agent 扮演什么角色、从哪里读取资料；
2. Dispatch：决定当前任务交给哪个角色；
3. Workflow Advancement：推动生产、审核、修改和复审等阶段转换；
4. Context Transfer：整理并复制不同对话之间的有效信息；
5. Progress Reconstruction：通过长对话或项目文件重新判断完成内容、当前状态和下一步。

共同矛盾是：

> 拆分角色会增加人工交接；不拆分角色又会导致职责混合和项目状态困在对话中。

因此，最核心的机会是：

> 让项目连续性属于项目本身，而不是属于某个对话；让角色可以分开，而不需要用户充当角色之间的传话人。

## 7. 已确认的权责边界

### 7.1 用户

- 提出项目想法；
- 审批有明确边界的短期目标；
- 决定产品目标、范围和优先级；
- 作出关键架构与高风险决策；
- 审核 Agent Engineering 方案；
- 验收阶段成果。

### 7.2 Agent

- 提供产品、项目和架构建议；
- 设计角色、任务、上下文和协作机制；
- 在已批准边界内完成编码、写作、测试、审核和修改；
- 记录成果、问题和交接信息。

### 7.3 项目运营工具

- 恢复项目状态；
- 为当前角色装载必要上下文；
- 推动任务和角色交接；
- 持续更新进度；
- 主动报告成果、风险和下一步；
- 在越界、阻塞或需要关键决策时通知用户。

## 8. 已确认的运行原则

- 每天由用户主动选择并启动项目；
- 工具不擅自决定用户今天推进哪个项目；
- 用户审批短期目标和执行边界，而不是审批 Agent 的每一个步骤；
- Agent 在已批准边界内可以持续执行；
- 自主执行不等于静默执行；
- 项目状态必须持续可见；
- 每次执行结束应生成摘要；
- 活跃项目应定期生成汇总；
- 完成、阻塞、越权、恢复和需要决策时应即时通知；
- 重要阶段按风险、范围变化和承诺程度审批，而不是按步骤数量审批；
- 角色代表职责，不绑定某个具体 Agent；
- Task Card 是执行、授权和交接载体，但不是所有项目知识的唯一载体；
- Agent 的文字报告本身不能证明任务完成，状态必须能被实际项目产物和验证结果支持。

## 9. 当前候选方向

当前推荐继续探索一个轻量的个人 AI 项目协调器。

它可能涉及项目状态、短期目标审批、角色上下文、Task、任务交接、进度报告、异常升级和恢复记录。

这些仍是候选能力，不是已经确认的 MVP 功能清单，也不代表最终系统架构。

## 10. 当前明确不做

- 完整个人 AI 工作站；
- 学习、笔记、日历、邮箱、浏览器和网站集成；
- 企业级多用户项目管理；
- 完整模拟公司的所有部门和职位；
- 为每个角色固定一个长期 Agent；
- 7×24 小时无人值守运行；
- 自动决定用户每天应该推进哪个项目；
- 未经批准自行开启新的短期目标；
- 让用户逐项批准所有细粒度任务；
- 当前确定 UI、数据库、Agent 框架或其他技术栈；
- 把所有信息塞入 Task Card；
- 为未来所有工作站模块提前设计通用平台。

## 11. 尚未解决的问题

- 项目当前状态的最小必要信息是什么；
- 哪些状态应由实际项目自动推导，哪些需要 Agent 更新；
- 如何避免项目状态成为与真实项目不同步的第二套系统；
- Global、Project、Role、Task 和临时上下文如何分层；
- 如何定义启动必读、角色必读、任务必读和条件读取；
- 如何判断一个短期目标的合理粒度；
- 哪些角色需要真正分离，哪些只是同一 Agent 的不同工作模式；
- 哪些流程可以确定性推进，哪些需要 Agent 判断；
- 如何保证任务交接同时包含实际项目、任务、变更证据和下一步，而不只是文字总结；
- 权限隔离是否必须进入第一版，以及它的最小可靠形式；
- 怎样的报告频率和内容既透明又不形成新的阅读负担。

## 12. 持续 Dogfooding 指标

后续不再用前置实验决定“是否开发”，而是在开发过程中持续观察：

- 用户手工搬运上下文的次数；
- 新 Agent 接手时需要的额外解释次数；
- 新 Agent 恢复项目状态所需时间和信息量；
- 任务状态与实际项目产物是否一致；
- Agent 是否遗漏状态更新和交接；
- 是否出现重复工作、角色混淆或越权；
- 进度报告是否准确且易于理解；
- 失败后是否能够恢复并保留记录。
